# как лучше записать в админке поле рекомендация пользователя клиента бизнесу

Для админки бизнес-клуба лучше назвать поле **«Рекомендация участника для бизнеса»** — это понятно и не создаёт путаницы, кто кому оставляет текст. В вашем контексте KCLUB, где есть участники и бизнес-профили, термин **«участник»** лучше, чем техническое «пользователь» или двусмысленное «клиент». [^1_1][^1_2]

## Лучший вариант

**Label:** `Рекомендация участника`
**Placeholder:** `Например: Рекомендую компанию за надёжность, качество сервиса и соблюдение договорённостей.`

Если поле размещено прямо в карточке компании, можно ещё короче:

- **Заголовок блока:** `Рекомендации`
- **Кнопка добавления:** `Оставить рекомендацию`
- **В админской таблице:** `Рекомендация участника`
- **Статус модерации:** `На модерации` / `Опубликована` / `Отклонена`


## Если это не отзыв

Выбери формулировку по смыслу данных:


| Что именно пишет участник | Название поля |
| :-- | :-- |
| Личный позитивный опыт работы | **Отзыв участника** |
| Готовность рекомендовать компанию другим | **Рекомендация участника** |
| Представление одного участника другому бизнесу | **Запрос на интродукцию** |
| Почему бизнес стоит добавить в каталог клуба | **Обоснование рекомендации бизнеса** |
| Внутренняя заметка менеджера клуба | **Комментарий администратора** |

Я бы не использовал **«Рекомендация пользователя клиента бизнесу»**: здесь неясны роли и направление рекомендации. Для вашей публичной роли `BUSINESS` и сущностей клуба наиболее чистая модель — **участник рекомендует бизнес**, поэтому в схеме/API удобно закрепить `memberRecommendation` или `businessRecommendation`, а в UI вывести «Рекомендация участника». [^1_1]

# тут участник рекомендует или представляет клиента бизнесу

Тогда это не «рекомендация бизнеса», а **интродукция клиента в бизнес**: участник передаёт бизнесу потенциального клиента или полезный контакт. Для такого сценария лучше использовать термин **«Представление клиента»** или **«Интро клиента»**, а не «рекомендация» — рекомендация обычно означает совет или отзыв, а не передачу конкретного лида. [^2_1]

## Как назвать в админке

**Оптимально и понятно:**

- **Сущность / раздел:** `Представления клиентов`
- **Кнопка у участника:** `Представить клиента бизнесу`
- **Поле с человеком:** `Кого представляет участник`
- **Поле с текстом:** `Комментарий к представлению`
- **В таблице:** `Представляющий участник` / `Представленный клиент` / `Бизнес`
- **Карточка записи:** `Представление клиента в [название бизнеса]`

Если интерфейс премиальный и частично англоязычный, можно оставить привычный клубный термин:

- **Раздел:** `Introductions`
- **Действие:** `Создать интродукцию`
- **Русская подпись:** `Представить клиента бизнесу`


## Рекомендуемая модель

| Сущность | Поле в БД / API | Отображение в UI |
| :-- | :-- | :-- |
| Участник, который делает интро | `introducedByMemberId` | Представляющий участник |
| Клиент или контакт | `introducedClientId` либо `clientName` | Представленный клиент |
| Бизнес-получатель | `businessId` | Бизнес |
| Причина или контекст | `message` | Комментарий к представлению |
| Этап обработки | `status` | Новый / В работе / Связались / Успешно / Неактуально |
| Согласие на передачу контакта | `consentConfirmedAt` | Согласие подтверждено |

Термин **«интродукция»** особенно уместен для бизнес-клуба: он подчёркивает ценность доверенного знакомства, а не механику реферальной программы с промокодом и вознаграждением. Реферальная модель обычно описывает ситуацию, когда существующий клиент приводит нового клиента, часто с отслеживаемым бонусом. [^2_1][^2_2]

Я бы в твоём KCLUB назвал сущность **`BusinessIntroduction`**, а в русской админке — **«Представление клиента бизнесу»**.

# опиши как в админке прописать поля, опции

Для KCLUB сделай отдельную сущность **«Представление клиента бизнесу»**: участник клуба создаёт доверенное интро, администратор контролирует согласие, передаёт контакт бизнесу и ведёт сделку по статусам. Это соответствует вашей ранее заложенной функции Business Introductions для VIP-участников. [^3_1][^3_2]

## Название раздела

**В сайдбаре админки:** `Представления клиентов`
**URL:** `/admin/introductions`
**Заголовок страницы:** `Представления клиентов бизнесу`
**Основная кнопка:** `Создать представление`

Не называй раздел «Рекомендации»: это будет восприниматься как отзыв о компании, а не передача конкретного потенциального клиента.

## Поля создания

| Поле в UI | API / БД-ключ | Тип | Обязательное | Опции или правило |
| :-- | :-- | --: | :--: | :-- |
| Представляющий участник | `introducedByMemberId` | Async select | Да | Искать по имени, email, телефону, номеру карты; показывать только `MEMBER` и `VIP` |
| Бизнес-получатель | `businessId` | Async select | Да | Только бизнесы со статусом `PUBLISHED` и активным партнёрством |
| Клиент / контакт | `clientType` | Select | Да | `PERSON` — физлицо; `COMPANY` — компания |
| Имя клиента | `clientName` | Text | Да | До 120 символов |
| Компания клиента | `clientCompany` | Text | Нет | Показывать обязательно, если `clientType = COMPANY` |
| Должность | `clientPosition` | Text | Нет | Например, CEO, Founder, Procurement Manager |
| Телефон | `clientPhone` | Phone input | Да | Формат E.164; например, `+380...` |
| Email | `clientEmail` | Email input | Нет | Валидировать формат |
| Предпочтительный канал связи | `preferredContactMethod` | Select | Да | `PHONE`, `WHATSAPP`, `TELEGRAM`, `EMAIL` |
| Причина знакомства | `reason` | Textarea | Да | Что нужно клиенту, почему ему релевантен этот бизнес; 20–1 000 символов |
| Контекст и детали | `note` | Textarea | Нет | Ограничения, бюджет, сроки, особенности коммуникации |
| Согласие клиента | `consentStatus` | Checkbox + select | Да | Чекбокс: `Клиент согласен на передачу контакта бизнесу`; источник: `VERBAL`, `WRITTEN`, `FORM` |
| Дата согласия | `consentConfirmedAt` | Datetime | Да | По умолчанию — текущее время |
| Владелец обработки | `assigneeAdminId` | Select | Нет | Сотрудник админки с ролью `OWNER`, `ADMIN`, `MODERATOR` или `SUPPORT` |
| Внутренняя заметка | `internalNote` | Textarea | Нет | Видна только сотрудникам; не передавать бизнесу |

Публичные роли в продукте остаются `MEMBER`, `VIP`, `BUSINESS`, а роли сотрудников — отдельный приватный контур админки; поэтому поле ответственного должно выбирать именно staff-пользователя, а не участника клуба. [^3_3][^3_4]

## Статусы процесса

Используй один основной статус `status`:


| Значение | Текст в UI | Когда ставить |
| :-- | :-- | :-- |
| `DRAFT` | Черновик | Админ начал оформление и ещё не подтвердил данные |
| `NEW` | Новое | Интро создано и ожидает первичной обработки |
| `REVIEWING` | На проверке | Проверяется согласие, полнота контактов и релевантность |
| `APPROVED` | Одобрено | Админ подтвердил, что интро можно передать бизнесу |
| `SENT_TO_BUSINESS` | Передано бизнесу | Контакт или запрос реально направлен бизнесу |
| `CONTACTED` | Бизнес связался | Бизнес подтвердил первый контакт с клиентом |
| `IN_PROGRESS` | В работе | Идут переговоры, встреча или подготовка предложения |
| `SUCCESSFUL` | Успешно | Целевое действие состоялось: сделка, встреча, контракт или иной результат |
| `DECLINED` | Отклонено | Нерелевантно, нет согласия, недостаточно данных и т. п. |
| `CLOSED` | Закрыто без результата | Контакт не состоялся, клиент отказался или запрос потерял актуальность |
| `CANCELLED` | Отменено | Участник или клиент отозвал представление до передачи |

Для MVP можно оставить семь состояний: `NEW`, `REVIEWING`, `APPROVED`, `SENT_TO_BUSINESS`, `IN_PROGRESS`, `SUCCESSFUL`, `CLOSED`. Остальные добавишь, когда появится реальная операционная статистика.

## Поля после передачи

После статуса `SENT_TO_BUSINESS` отобрази отдельную секцию **«Обработка бизнесом»**:


| Поле | API / БД-ключ | Тип |
| :-- | :-- | :-- |
| Дата передачи | `sentToBusinessAt` | Автоматическое datetime |
| Способ передачи | `deliveryMethod` | `EMAIL`, `CRM`, `MANUAL`, `MESSENGER` |
| Контакт бизнеса | `businessContactId` | Select из контактов компании |
| Дата первого контакта | `firstContactAt` | Date |
| Результат первого контакта | `firstContactOutcome` | `PENDING`, `CONNECTED`, `NO_RESPONSE`, `DECLINED` |
| Потенциальная ценность | `estimatedValue` | Decimal + валюта |
| Итог | `outcome` | `MEETING_BOOKED`, `PROPOSAL_SENT`, `DEAL_WON`, `DEAL_LOST`, `NOT_RELEVANT` |
| Причина закрытия | `closeReason` | Select + текстовое пояснение |
| Комментарий бизнеса | `businessFeedback` | Textarea |
| Дата закрытия | `closedAt` | Автоматическое datetime |

`estimatedValue` не обязательно показывать всем администраторам: это чувствительные коммерческие данные, поэтому доступ к нему лучше ограничить `OWNER` и `ADMIN`.

## Таблица списка

На странице `/admin/introductions` выведи:

- ID интро — например, `INT-000124`
- Статус
- Дата создания
- Представляющий участник
- Клиент / компания
- Бизнес-получатель
- Ответственный сотрудник
- Последнее обновление
- Следующее действие / дата follow-up

Фильтры:

- Статус
- Бизнес
- Представляющий участник
- Ответственный
- Дата создания
- Наличие подтверждённого согласия
- Результат: успешно / без результата / в работе
- Просроченный follow-up

Сортировка по умолчанию: сначала `NEW` и `REVIEWING`, затем записи с ближайшим `nextFollowUpAt`, после — все остальные по `createdAt DESC`.

## Карточка интро

Сделай карточку с четырьмя вкладками:

1. **Обзор** — участник, клиент, бизнес, причина, статус, таймлайн.
2. **Контакт и согласие** — телефон, email, канал связи, источник и дата согласия.
3. **Обработка** — ответственный, follow-up, обратная связь бизнеса, исход.
4. **Внутренние заметки** — только staff-комментарии и журнал изменений.

Вместо перезаписи важных данных веди `activity log`: кто, когда и с какого на какой статус перевёл интро; кто изменил контакт клиента; когда передал данные бизнесу. Для админ-продукта с раздельными staff-ролями это создаёт нормальную операционную прозрачность. [^3_1][^3_3]

## Минимальный DTO

```ts
type IntroductionStatus =
  | 'DRAFT'
  | 'NEW'
  | 'REVIEWING'
  | 'APPROVED'
  | 'SENT_TO_BUSINESS'
  | 'CONTACTED'
  | 'IN_PROGRESS'
  | 'SUCCESSFUL'
  | 'DECLINED'
  | 'CLOSED'
  | 'CANCELLED'

type CreateBusinessIntroductionDto = {
  introducedByMemberId: string
  businessId: string

  clientType: 'PERSON' | 'COMPANY'
  clientName: string
  clientCompany?: string
  clientPosition?: string
  clientPhone: string
  clientEmail?: string
  preferredContactMethod: 'PHONE' | 'WHATSAPP' | 'TELEGRAM' | 'EMAIL'

  reason: string
  note?: string

  consentConfirmed: true
  consentSource: 'VERBAL' | 'WRITTEN' | 'FORM'
  consentConfirmedAt: string

  assigneeAdminId?: string
  internalNote?: string
}
```

Критичное правило: **нельзя переводить интро в `APPROVED` или `SENT_TO_BUSINESS`, пока `consentConfirmed !== true`**. Это лучше валидировать на backend, а не только отключённой кнопкой в интерфейсе.

# нужно добавить менеджера, который ведёт сделку

Да — добавь отдельное обязательное поле **«Менеджер сделки»**. Это не просто технический `assignee`: менеджер является владельцем процесса, отвечает за коммуникацию с участником, бизнесом и за финальный результат интродукции. В вашей модели его нужно выбирать из приватных staff-пользователей, а не из публичных ролей `MEMBER` / `VIP` / `BUSINESS`. [^4_1][^4_2]

## Поле в форме

| Поле в UI | Ключ API / БД | Тип | Обязательное | Логика |
| :-- | :-- | --: | :--: | :-- |
| Менеджер сделки | `dealManagerId` | Async select | Да | Выбор сотрудника, который ведёт сделку |
| Менеджер сделки | `dealManagerSnapshot` | Автоснимок | Да | Имя и email на момент назначения, чтобы история не ломалась при изменении профиля |
| Дата назначения | `assignedAt` | Datetime | Авто | Ставится при первом выборе менеджера |
| Назначил | `assignedByAdminId` | Reference | Авто | Текущий администратор, который назначил менеджера |
| Следующий контакт | `nextFollowUpAt` | Datetime | Нет, но рекомендовано | Обязателен после статуса `SENT_TO_BUSINESS` |
| Последний контакт | `lastContactAt` | Datetime | Авто/вручную | Обновляется через действие «Зафиксировать контакт» |

### Опции списка менеджеров

В селекте показывай сотрудников со специальной внутренней ролью или правом:

```ts
type StaffRole = 'OWNER' | 'ADMIN' | 'MODERATOR' | 'SUPPORT' | 'DEAL_MANAGER'
```

Но лучше не смешивать роль доступа и должность. Сохрани системные права (`OWNER`, `ADMIN`, `MODERATOR`, `SUPPORT`) как есть, а для сотрудников добавь отдельные поля:

```ts
type StaffProfile = {
  id: string
  userId: string
  jobTitle?: string              // Например: Partnership Manager
  canManageIntroductions: boolean
  isAvailableForDeals: boolean
  activeIntroductionsCount: number
}
```

Тогда в поле **«Менеджер сделки»** отображай только сотрудников, у которых `canManageIntroductions = true` и `isAvailableForDeals = true`. Это позволяет, например, дать Support доступ к просмотру карточек без права вести коммерческие сделки. Подход согласуется с вашим разделением публичных и внутренних staff-ролей. [^4_1][^4_3]

## Поля в таблице

Добавь в `/admin/introductions`:

- **Менеджер сделки** — аватар, имя, статус доступности.
- **Следующее действие** — дата и короткий текст, например: «Уточнить потребность у клиента».
- **Последняя активность** — дата последней записи в журнале.
- **SLA** — бейдж: `В срок`, `Сегодня`, `Просрочено`.
- **Статус сделки** — отдельно от статуса самого представления, если позднее появится воронка продаж.

Фильтры:

- Менеджер сделки: конкретный сотрудник / `Не назначен`
- Только мои сделки
- Свободные интро: записи без `dealManagerId`
- Просроченный follow-up
- Нагрузка: 0–5 / 6–15 / 16+ активных сделок


## Действия менеджера

В карточке интро закрепи верхний блок:

```text
Менеджер сделки: [ Анна Коваленко ▾ ]
Следующее действие: [ 31 июля, 14:00 ]
[ Зафиксировать контакт ] [ Передать другому менеджеру ]
```

Менеджер может:

- Взять свободное интро в работу — действие `Взять сделку`.
- Менять рабочие статусы от `NEW` до `CLOSED`.
- Записывать звонки, сообщения, встречи и договорённости в таймлайн.
- Назначать дату и содержание следующего действия.
- Фиксировать результаты: встреча назначена, КП отправлено, сделка успешна или закрыта без результата.
- Передавать сделку другому менеджеру с обязательным комментарием.

`OWNER` и `ADMIN` могут назначать или переназначать любого менеджера; `DEAL_MANAGER` — брать свободные сделки и вести только собственные; `SUPPORT` — видеть данные, но не менять коммерческий результат. Это полезно вынести в permissions, а не жёстко привязывать к интерфейсу. [^4_3][^4_1]

## Статусы назначения

Не создавай отдельную сущность «назначение» для MVP, если не нужны несколько участников одной сделки. Достаточно добавить в `BusinessIntroduction`:

```ts
type BusinessIntroduction = {
  id: string
  status: IntroductionStatus

  introducedByMemberId: string
  businessId: string

  dealManagerId: string | null
  assignedAt: string | null
  assignedByAdminId: string | null

  nextFollowUpAt: string | null
  lastContactAt: string | null

  createdAt: string
  updatedAt: string
}
```

Правила:

- При `NEW` поле менеджера может быть пустым, чтобы запись попала в очередь.
- При переходе в `REVIEWING`, `APPROVED`, `SENT_TO_BUSINESS` и далее `dealManagerId` должен быть заполнен.
- При переназначении сохраняй запись в `IntroductionActivity`: старый менеджер, новый менеджер, кто изменил и комментарий.
- Нельзя закрыть сделку (`SUCCESSFUL`, `CLOSED`, `DECLINED`) без финального результата и комментария менеджера.


## Отдельно про «менеджера»

В интерфейсе пиши именно **«Менеджер сделки»**, а не «Ответственный». «Ответственный» можно оставить как более общее техническое поле для администратора или модератора, а «Менеджер сделки» ясно говорит, кто реально ведёт клиента до результата.
